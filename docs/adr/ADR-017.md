# ADR-017: Independent verification trust boundary

**Status:** accepted

**Date:** 28 July 2026

**Depends on:** ADR-014, ADR-015, ADR-016

## Context

An executor can run tests and report that they pass, but this is not independent evidence.
The same executor may have:

- changed tests or test scripts;
- selected only an easy subset;
- run against dirty or uncommitted state;
- used credentials unavailable in normal verification;
- ignored required acceptance criteria;
- produced an inaccurate completion summary.

A second model reading the executor's summary is also not independent verification. It
inherits the claim rather than reproducing the check.

RoleFlock needs a trust boundary that separates:

- executor claims;
- deterministic command attestations;
- model-based criterion judgement;
- final acceptance authority.

## Decision

Required verification runs outside the executor's write environment against the exact
result commit and a frozen Verification Specification.

Verification has two distinct components:

1. `Deterministic Test Runner` executes exact approved checks and creates attestations.
2. `Verifier` evaluates the Change Contract using those attestations and read-only
   inspection.

Neither component may modify the result being assessed.

## Verification subject

Every verification run binds to:

```typescript
interface VerificationSubject {
  repositoryId: string;
  baseCommit: string;
  resultCommit: string;
  diffDigest: string;
  contractHash: string;
  planHash: string;
  verificationSpecHash: string;
}
```

Verification of dirty, unstaged, or uncommitted writer state cannot satisfy required
evidence. The executor must produce a result commit or equivalent immutable tree digest.

## Frozen Verification Specification

The specification is approved before executor writes begin and includes:

- criterion IDs;
- exact command and argv;
- working directory;
- required environment/tool constraints;
- expected artifact types;
- timeout and resource budget;
- network policy;
- secret references;
- test-mutation policy;
- browser/database/schema assertions;
- required manual or model review;
- pass/fail semantics.

The executor cannot mutate the specification. A necessary verification change returns to
the planner or test designer and creates a new plan/specification version.

## Clean verifier workspace

RoleFlock creates a verifier workspace from the result commit:

- separate from the writer worktree;
- clean Git state;
- read-only source mount where supported;
- isolated temporary/output directories;
- no writer process or lease;
- no inherited writer credentials;
- restricted network according to verification policy;
- reproducible setup or an explicitly recorded environment.

The verifier workspace records:

- repository and commit identity;
- OS/platform;
- runtime and tool versions;
- dependency lockfile digests;
- container/image digest when applicable;
- setup and maintenance commands;
- environment variables by name and redacted digest, never secret value;
- effective filesystem and network policy.

## Credential separation

Verification receives no writer credential by default.

When a check requires a secret:

- policy names the required secret capability;
- a short-lived verifier-scoped credential is issued;
- the credential is unavailable to the model unless the tool specifically requires it;
- the value is redacted from logs and attestations;
- issuance and revocation are audited.

A writer-scoped credential cannot be reused merely because it is convenient.

## Deterministic Test Runner

The runner:

- executes exact argv without shell interpolation;
- applies timeout, resource, filesystem, and network policy;
- captures stdout, stderr, exit status, signal, duration, and output artifact digests;
- records command and environment identity;
- cannot choose alternate commands;
- cannot interpret a result as satisfying an unspecified criterion;
- cannot edit source.

```typescript
interface VerificationAttestation {
  id: string;
  subject: VerificationSubject;
  checkId: string;
  commandDigest?: string;
  environmentDigest: string;
  startedAt: string;
  completedAt: string;
  outcome: 'pass' | 'fail' | 'error' | 'timeout' | 'unknown';
  exitCode?: number;
  signal?: string;
  logDigests: string[];
  artifactDigests: string[];
  runnerIdentity: RunnerIdentityRef;
  signature?: SignatureEnvelope;
}
```

Unknown and infrastructure error are not PASS.

## Verifier

The verifier receives:

- authorised Change Contract;
- approved Execution Plan;
- frozen Verification Specification;
- result commit and diff;
- executor report as an untrusted claim;
- deterministic attestations;
- policy and disclosure records.

It emits a verdict for every acceptance criterion:

```typescript
interface CriterionVerdict {
  criterionId: string;
  outcome: 'pass' | 'fail' | 'insufficient_evidence' | 'not_applicable';
  evidenceRefs: string[];
  findingIds: string[];
  explanation: string;
}
```

Rules:

- required deterministic evidence cannot be replaced by model judgement;
- executor output cannot be the sole evidence for a PASS;
- every PASS references evidence bound to the same subject;
- insufficient evidence is distinct from functional failure;
- verifier findings route to the planner;
- verifier cannot repair source or revise the plan.

## Test and verification mutation detection

RoleFlock compares the base and result commits for:

- test files;
- package/build scripts;
- CI configuration;
- verification helpers;
- snapshots and fixtures;
- policy configuration.

The plan declares one of:

```text
forbid
review
allow_planned
```

Behaviour:

- `forbid`: any relevant mutation blocks verification;
- `review`: mutation requires a dedicated finding and approval;
- `allow_planned`: only exact planned mutation classes/paths are accepted.

Changing a command alias, package script, or test selector is treated as verification
mutation even when the nominal command string remains the same.

## Evidence independence levels

Verification records an explicit level:

```text
executor_claim
separate_invocation
different_model
different_model_family
different_provider
clean_local_runner
organisation_trusted_runner
externally_attested_runner
```

These values describe properties; they are not a single ordinal score. Policy specifies
the required combination for a task.

Examples:

- low risk may require clean local runner plus separate verifier invocation;
- high risk may require clean runner plus different model family;
- critical risk may require organisation-trusted runner and different provider verifier.

The UI never labels executor claim or same dirty workspace as independent verification.

## Evidence reuse

An attestation may be reused only when all bound inputs remain identical:

- result commit;
- contract hash;
- plan hash when the check depends on implementation decisions;
- verification specification hash;
- environment policy and relevant toolchain digest.

Reuse is recorded explicitly. Matching command text alone is insufficient.

A contract or plan revision invalidates evidence when the changed semantics affect the
criterion or check. Conservative policy reruns when the impact is unknown.

## Failure routing

```text
Runner infrastructure error
→ retry only if idempotency and budget policy permit
→ otherwise operator

Deterministic check failure inside repair envelope
→ executor bounded repair

Deterministic check failure outside repair envelope
→ planner

Verifier functional or evidence finding
→ planner

Verification specification gap
→ planner/test designer
→ new plan/spec version
```

No failure routes directly to acceptance.

## Local and organisation trust

A clean local runner provides separation from the writer process but remains controlled by
one workstation owner. It creates local assurance.

Organisation assurance requires:

- registered runner identity;
- protected signing key;
- centrally recognised policy;
- revocation;
- durable audit history.

RoleFlock displays the achieved trust properties rather than implying that all signed
evidence has equal independence.

## Consequences

### Positive

- writer self-report cannot satisfy required verification;
- test weakening and command drift become visible;
- evidence binds to immutable repository state;
- deterministic checks and model judgement have distinct roles;
- verification strength can scale with risk.

### Negative

- clean workspaces increase latency, storage, and compute;
- environment setup may be difficult for stateful projects;
- credential separation requires new infrastructure;
- some checks cannot be fully reproduced locally.

## Alternatives considered

### Trust executor test output

Rejected because the writer controls the code, tests, scripts, and narrative.

### Use only an independent reviewing model

Rejected because a model cannot reproduce deterministic evidence from summaries alone.

### Run verification in the writer worktree

Rejected for required assurance because dirty state and writer-controlled environment
weaken subject identity and reproducibility.

### Require remote verification for every task

Rejected for local-first MVP. Clean local verification is useful when labelled honestly;
organisation trust is an additional level.

## Implementation requirements

- `packages/verification-runner`;
- frozen Verification Specification schemas;
- clean verifier worktree lifecycle;
- restricted exact-argv command execution;
- environment and subject digests;
- credential separation;
- test/script mutation analysis;
- structured criterion verdicts;
- attestation storage and later signing;
- recovery and cleanup semantics.

## Acceptance evidence

This ADR is implemented when:

- executor cannot change the frozen specification;
- required checks run from the exact result commit in a clean verifier workspace;
- writer credentials are absent;
- modified test/script behaviour is detected according to policy;
- every required criterion has a structured verdict and bound evidence;
- executor claims alone cannot produce PASS;
- restart recovery cannot attach an attestation to the wrong subject.
