# ADR-015: Versioned Change Contract and Execution Plan

**Status:** accepted

**Date:** 28 July 2026

**Depends on:** ADR-014

## Context

RoleFlock currently stores a task brief and compiles role-specific prompts, but a prose
brief is not a durable authority boundary. It does not precisely identify:

- which requirements are authoritative;
- what acceptance means;
- which outcomes are forbidden;
- which implementation decisions have been approved;
- whether later feedback changes intent or only implementation;
- which version an executor followed.

An executor that receives a brief, repository context, and feedback can silently make
product or architecture decisions. A verifier may then assess a result against a different
interpretation. Conversation history cannot resolve this reliably across fresh invocations,
different providers, external agents, or multiple reviewers.

RoleFlock needs two separate artifacts:

1. an authority-owned statement of the desired outcome;
2. a planner-owned implementation decision record.

Combining them would allow a planner to alter requirements while revising implementation.

## Decision

Every new write task uses two immutable, versioned artifacts:

- `ChangeContract`: authorised intent and acceptance;
- `ExecutionPlan`: approved implementation decisions for one exact contract version.

Both artifacts are canonicalised, hashed, durably stored, and referenced by hash in all
downstream execution, verification, approval, and passport records.

### Change Contract ownership

The contract authority is a human or organisation policy with authority over the requested
outcome. A model may draft or clarify the contract but cannot authorise it.

The contract owns:

- objective;
- acceptance criteria with stable criterion IDs;
- prohibited outcomes;
- out-of-scope statements;
- risk classification;
- required evidence;
- authority sources;
- unresolved questions;
- approval identity and time.

The contract does not prescribe code-level implementation unless that implementation is an
authoritative requirement.

### Execution Plan ownership

The planner owns the plan. The plan is constrained by one exact authorised contract hash.

The plan owns:

- implementation steps;
- mapping from steps to acceptance criteria;
- expected and allowed paths;
- forbidden paths;
- allowed operation classes;
- planned dependency or migration changes;
- verification specification;
- change budget;
- repair envelope;
- assumptions, decisions, and risks.

The plan cannot weaken or reinterpret its contract. A planner that discovers a requirement
conflict creates a clarification request to the contract authority.

## Lifecycle

### Change Contract

```text
DRAFT
→ NEEDS_CLARIFICATION
→ AWAITING_AUTHORISATION
→ AUTHORISED
→ SUPERSEDED or WITHDRAWN
```

Rules:

- only `DRAFT` and `NEEDS_CLARIFICATION` content may be edited;
- authorisation creates an immutable version;
- revision creates a new version with `parentVersionId` and `changeReason`;
- the prior version becomes `SUPERSEDED`, but remains readable;
- withdrawal prevents new plans and executions;
- an authorised version cannot return to draft.

### Execution Plan

```text
PROPOSED
→ NEEDS_REVISION
→ AWAITING_APPROVAL
→ APPROVED
→ SUPERSEDED or CANCELLED
```

Rules:

- an approved plan is immutable;
- revision creates a new version linked to its parent;
- only one plan version may be active for an executor attempt;
- a plan is invalid when its contract is superseded or withdrawn;
- a plan cannot move to approved while blocking critique findings remain open;
- cancellation preserves the plan and decision history.

## Canonical identity

Artifact identity is derived from canonical semantic content, excluding mutable projection
fields such as UI labels.

```typescript
interface ArtifactIdentity {
  id: string;
  version: number;
  hashAlgorithm: "sha256";
  hash: string;
}
```

The contract hash includes:

- task and repository identity;
- semantic contract fields;
- authority source digests;
- version and parent reference;
- authorising actor.

The plan hash includes:

- contract ID and hash;
- semantic plan fields;
- verification specification digest;
- version and parent reference;
- proposing and approving identities.

Canonicalisation must:

- use stable field ordering;
- reject duplicate criterion and step IDs;
- preserve array ordering when order has meaning;
- sort set-like collections before hashing;
- distinguish absent, unknown, empty, and false;
- normalise repository paths;
- reject non-finite numbers and invalid timestamps.

## Execution pinning

An executor invocation stores:

```typescript
interface ExecutionPin {
  taskId: string;
  contractId: string;
  contractVersion: number;
  contractHash: string;
  planId: string;
  planVersion: number;
  planHash: string;
  baseCommit: string;
}
```

Before any write or command, the runtime checks that:

- the contract is authorised and not superseded or withdrawn;
- the plan is approved and not superseded or cancelled;
- the plan references the exact contract hash;
- the invocation pin matches durable state;
- repository base state satisfies the plan's base policy.

A mismatch blocks the action and emits a typed stale-artifact event.

## Revision and invalidation

### Contract revision

A new authorised contract version:

- invalidates all unstarted plans for the prior contract;
- stops new executor attempts from starting;
- requests cooperative stop for a running executor at the next safe boundary;
- requires the planner to produce a new plan;
- invalidates unissued PASS passport candidates.

Prior evidence remains attached to the version under which it was produced.

### Plan revision

A new approved plan version:

- invalidates unstarted executor attempts using the prior version;
- cooperatively stops a running attempt when continuing could violate the new plan;
- requires a new execution report;
- retains deterministic evidence that is still cryptographically and semantically valid;
- requires verification to bind to the new plan hash.

Evidence reuse must be explicit; it cannot be inferred from matching prose.

## Low-risk tasks

Every write still requires a plan. For low-risk tasks, RoleFlock may generate a micro-plan
with:

- one or more bounded steps;
- explicit allowed paths;
- no dependency, migration, architecture, or external-side-effect changes;
- a small change budget;
- deterministic verification;
- policy-based automatic plan approval.

Planning and execution remain separate invocations and permission scopes even when they use
the same provider/model.

## Storage

SQLite stores append-only artifact versions and mutable projections separately.

Required logical records:

```text
change_contracts
change_contract_versions
execution_plans
execution_plan_versions
artifact_authorisations
artifact_links
```

Version rows are insert-only after authorisation or approval. Status transitions are
recorded as events; projections may be rebuilt.

Optimistic concurrency uses aggregate version. A stale command receives a conflict and
must reload rather than overwriting a newer decision.

## Context distribution

Roles receive artifacts according to authority:

- contract planner: brief and authority sources;
- contract authority: draft contract and conflicts;
- planner: exact authorised contract plus read-only repository evidence;
- plan critic: contract and proposed plan;
- executor: approved plan, required contract subset, and permitted repository context;
- verifier: complete contract, plan, execution report, result diff, and independent evidence;
- release approver: review packet and passport candidate.

Raw feedback is never substituted for a revised artifact.

## Consequences

### Positive

- intent changes and implementation changes become distinguishable;
- every executor action can be evaluated against one plan version;
- feedback no longer relies on lost conversation context;
- verification and approval bind to stable semantics;
- external agents can participate through portable artifacts;
- historical outcome measurement can distinguish planner and executor failures.

### Negative

- even small tasks require artifact creation;
- revisions create more state and UI complexity;
- cooperative stop and evidence reuse require careful semantics;
- users must authorise requirements rather than relying only on a prompt.

## Alternatives considered

### Store only the task brief

Rejected because it is mutable prose without criterion identity, authority, or versioned
implementation decisions.

### Combine contract and plan

Rejected because it lets the planner change requirements while revising implementation.

### Store only conversation history

Rejected because history is provider-specific, difficult to validate, and unsuitable as a
portable authority record.

### Allow executor plan edits

Rejected because it collapses the planner/executor authority boundary and makes deviations
invisible.

## Implementation requirements

The implementation must provide:

- schema and semantic validators;
- canonical hash functions with golden vectors;
- immutable version repositories;
- optimistic concurrency;
- explicit authorisation/approval fingerprints;
- artifact-gated graph nodes;
- stale-artifact stop behaviour;
- legacy task labelling without invented contracts;
- API and UI version history.

## Acceptance evidence

This ADR is implemented when:

- a new write task cannot start without an authorised contract and approved plan;
- authorised/approved versions cannot be mutated;
- contract revision invalidates dependent plans;
- plan revision invalidates stale executor attempts;
- executor, verifier, approval, and passport records contain exact artifact hashes;
- restart recovery preserves the same execution pin.
