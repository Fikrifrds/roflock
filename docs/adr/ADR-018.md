# ADR-018: Portable Change Passport and signing

**Status:** accepted

**Date:** 28 July 2026

**Depends on:** ADR-014, ADR-015, ADR-017

## Context

RoleFlock currently exports evidence bundles with content hashes. A hash can detect that a
bundle changed after it was created, but it does not prove:

- who issued it;
- which runner produced the evidence;
- whether the database was changed before export;
- whether evidence belongs to the stated commit;
- whether the contract and plan were authorised;
- whether the issuer is trusted or revoked;
- whether required verification actually ran independently.

Vendor session logs are also insufficient as a portable acceptance artifact. They describe
one provider's activity but do not bind cross-provider execution, independent verification,
policy, and human approval to one immutable software result.

RoleFlock needs a verifiable artifact that can travel with a commit or pull request and be
validated without trusting the RoleFlock web UI.

## Decision

RoleFlock issues a signed, portable `ChangePassport` for a specific repository result.

The passport binds:

- authorised Change Contract;
- approved Execution Plan;
- Verification Specification;
- base and result commits;
- diff digest;
- execution attestations;
- independent verification attestations;
- policy decisions;
- approval identities;
- disclosure manifests;
- unresolved risks;
- final verdict and assurance properties.

The format adapts established in-toto attestation and DSSE conventions where practical.
RoleFlock does not invent a proprietary cryptographic primitive.

## Subject identity

```typescript
interface PassportSubject {
  repositoryId: string;
  repositoryRemoteDigest?: string;
  baseCommit: string;
  resultCommit: string;
  treeDigest: string;
  diffDigest: string;
}
```

A passport is valid only for the exact subject. A new commit, amended commit, force push,
or changed tree invalidates the prior merge status even when the task ID is unchanged.

## Passport payload

```typescript
interface ChangePassportPayload {
  schemaVersion: string;
  passportId: string;
  taskId: string;
  subject: PassportSubject;

  contract: ArtifactDigestRef;
  plan: ArtifactDigestRef;
  verificationSpecification: ArtifactDigestRef;

  executionAttestations: AttestationRef[];
  verificationAttestations: AttestationRef[];
  policyDecisions: PolicyDecisionRef[];
  approvals: ApprovalRef[];
  disclosures: DisclosureManifestRef[];
  deviations: DeviationRef[];
  unresolvedRisks: RiskRecord[];

  verdict: "pass" | "fail" | "conditional" | "revoked";
  assurance: AssuranceProperties;
  issuedAt: string;
  expiresAt?: string;
}
```

Large logs and artifacts may be referenced by digest rather than embedded. Required
evidence availability is declared so a verifier can distinguish:

- embedded and verified;
- externally retrievable and verified;
- digest-only;
- unavailable.

Digest-only evidence cannot satisfy policy that requires inspectable evidence.

## Signed envelope

The payload is canonicalised and signed in a DSSE-compatible envelope:

```typescript
interface SignedChangePassport {
  payloadType: string;
  payload: string;
  signatures: Array<{
    keyid: string;
    sig: string;
  }>;
}
```

Initial signing algorithm support:

- Ed25519 for local installation and organisation runner identities.

Algorithm identifiers, key IDs, and payload type are explicit and versioned. Signature
verification never relies on a filename or UI-supplied issuer label.

## Issuer and runner identities

```typescript
interface RunnerIdentity {
  id: string;
  kind: "local_installation" | "organisation_runner" | "external_attestor";
  publicKey: string;
  issuer?: string;
  validFrom: string;
  validUntil?: string;
  status: "active" | "rotated" | "revoked";
}
```

### Local installation

- private key is generated on first use;
- private key is stored in OS keychain through `secret-store`;
- SQLite stores only public identity and key reference;
- passports are labelled local self-attestation;
- workstation owner remains inside the trust boundary.

### Organisation runner

- runner is registered by organisation authority;
- key scope and repository permissions are recorded;
- rotation and revocation are supported;
- trust roots are distributable to offline verifiers;
- organisation policy determines acceptable issuer identities.

### External attestor

Future integrations may accept signatures from approved CI, build, or provenance systems.
External trust is policy-configured and never inferred from a valid signature alone.

## Assurance properties

The passport reports achieved properties rather than one misleading score:

```typescript
interface AssuranceProperties {
  intent: "authorised" | "draft" | "legacy_uncontracted";
  plan: "approved" | "unapproved" | "absent";
  execution: "roleflock_managed" | "external_observed" | "external_incomplete";
  verification:
    | "executor_claim_only"
    | "clean_local_runner"
    | "organisation_trusted_runner"
    | "external_attested_runner";
  verifierIndependence: IndependenceProperty[];
  issuerTrust: "local_self" | "organisation" | "external";
  evidenceAvailability: "complete" | "partial" | "digest_only";
}
```

A signature proves that an issuer signed a payload. It does not by itself prove that the
issuer, runner, evidence, or process satisfies a buyer's policy.

## Issuance rules

A PASS passport may be issued only when:

- contract is authorised and current;
- plan is approved and current;
- subject commit matches execution and verification;
- all blocking acceptance criteria pass;
- all required evidence is present;
- no open blocking deviation exists;
- required verification and independence policies are satisfied;
- required approvals bind exact artifact hashes and result commit;
- issuer identity is active;
- graph/run state is terminal and internally consistent.

Conditional passports:

- list every unsatisfied or waived condition;
- identify the authority that accepted each waiver;
- cannot satisfy a policy requiring unconditional PASS.

FAIL passports may be issued for audit but cannot satisfy a merge gate.

## Event-time integrity

Evidence integrity must not begin only at export time.

Assurance events are chained:

```typescript
interface AttestedEvent {
  eventId: string;
  aggregateId: string;
  sequence: number;
  previousHash?: string;
  payloadHash: string;
  eventHash: string;
  actor: ActorRef;
  createdAt: string;
}
```

The passport includes or references the terminal event-chain digest. The issuer verifies
the chain before signing.

This detects post-event modification relative to the issuer identity. Organisation or
external anchoring is required to protect against a local owner replacing both local data
and local keys.

## Revocation and expiry

A passport may be revoked when:

- its result commit is replaced;
- evidence is later found invalid;
- an approval is withdrawn;
- issuer key is compromised;
- policy changes require explicit revocation;
- an escaped defect invalidates the assurance claim.

Revocation record:

```typescript
interface PassportRevocation {
  passportId: string;
  payloadDigest: string;
  reason: string;
  revokedBy: ActorRef;
  revokedAt: string;
  signature: SignatureEnvelope;
}
```

Offline verification reports that revocation status is unknown when no current revocation
source is available. It must not report active merely because the original signature is
valid.

Expiry is optional and policy-driven. Expired is distinct from revoked.

## Redaction and privacy

The public or client-facing passport may omit sensitive content while preserving:

- artifact type;
- digest;
- issuer;
- result;
- availability policy.

Redaction occurs before signing the distributable payload. A recipient can verify what was
shared but cannot infer hidden content.

RoleFlock may issue multiple views for one result:

- internal full passport;
- client-redacted passport;
- public summary.

Each view has its own payload digest and signature and references the same subject and
underlying attestation digests.

Secrets, raw credentials, and unredacted environment values are never embedded.

## Schema compatibility

Passport schema uses semantic versioning:

- patch: clarification without wire change;
- minor: backward-compatible optional fields;
- major: incompatible semantics or required fields.

Verifiers:

- reject unsupported major versions;
- preserve unknown optional fields when forwarding;
- never ignore an unknown required policy predicate;
- expose exact schema and payload type.

Golden fixtures and conformance tests are published with the schema.

## Standalone verification

The product provides:

```text
roleflock passport verify <passport>
```

Verification checks:

1. envelope and signature;
2. issuer key identity and validity;
3. schema and canonical payload;
4. subject commit/tree/diff when repository is available;
5. artifact and attestation digests;
6. event-chain digest;
7. approval bindings;
8. expiry and available revocation data;
9. caller-supplied policy/trust roots.

Output is structured and human-readable:

```text
VALID SIGNATURE
SUBJECT MATCH
POLICY PASS
ASSURANCE: local self-attestation + clean local runner
REVOCATION STATUS: current / revoked / unknown
```

Cryptographic validity and policy acceptance are reported separately.

## Git integration

Passports may be:

- stored in RoleFlock data storage;
- attached to a pull request/check run;
- published to an OCI or attestation store;
- referenced from commit metadata;
- exported as a file.

The GitHub/GitLab status check resolves the passport by result commit and validates it
against current policy. The status is invalidated on a new commit or revocation.

## Consequences

### Positive

- acceptance evidence becomes portable and commit-bound;
- clients and reviewers do not need access to one vendor's agent session;
- local and organisation assurance can be distinguished honestly;
- merge systems can enforce a machine-readable result;
- tampering, expiry, and revocation have explicit semantics.

### Negative

- signing key lifecycle adds operational complexity;
- offline revocation cannot always be current;
- evidence storage and retrieval require retention policy;
- standards integration and compatibility testing increase implementation cost.

## Alternatives considered

### Keep the current root hash only

Rejected because it has no issuer identity or trust/revocation semantics and can be
recomputed after local data changes.

### Store only raw logs

Rejected because logs are large, provider-specific, and do not express an acceptance claim.

### Use signed Git commits alone

Rejected because commit signatures identify authorship but do not bind contract,
verification, policy, and approval evidence.

### Invent a proprietary signature format

Rejected in favour of established envelope and attestation conventions.

## Implementation requirements

- `packages/change-passport`;
- event-chain support in evidence storage;
- OS-keychain-backed local identity;
- signature issue/verify/revoke APIs;
- schema fixtures and conformance tests;
- trust-root and assurance-property evaluation;
- standalone verification CLI;
- review packet and passport UI;
- commit-bound Git status integration in a later milestone.

## Acceptance evidence

This ADR is implemented when:

- any payload mutation invalidates signature verification;
- a passport cannot validate for another commit/tree;
- PASS cannot issue with stale contract/plan, missing evidence, or open deviation;
- local and organisation trust are visibly distinct;
- revocation and expiry produce distinct results;
- offline CLI verification succeeds with supplied trust roots;
- legacy export hashes are never represented as signed passports.
