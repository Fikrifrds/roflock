# ADR-014: Independent delivery-assurance boundary

**Status:** accepted

**Date:** 28 July 2026

**Related:** ADR-013. This ADR preserves its rejection of interactive-loop competition
and refines unattended parallel execution from primary differentiation to required parity.

## Context

RoleFlock began as a local-first control plane that invokes coding agents through a
planner, reviewer, writer, test, verifier, and acceptance graph.

That runtime remains useful, but the execution primitives are not a durable product
boundary. Coding-agent products increasingly provide:

- parallel agents;
- background execution;
- isolated worktrees;
- custom roles and subagents;
- hooks and policy checks;
- test execution;
- session logs and audit events;
- interactive follow-up and IDE handoff.

RoleFlock invokes many of the same agents users can run directly. It cannot claim an
inherent intelligence advantage over those agents, and an additional workflow is a net
cost when a developer is performing fast interactive iteration.

The durable problem begins after organisations delegate more work than they can cheaply
review. A coding agent can propose and implement a change, but it must not independently
grant itself:

- authority to reinterpret requirements;
- permission to expand scope;
- permission to access protected resources;
- authority to choose weaker evidence;
- authority to verify its own claims;
- permission to merge or release its output.

An organisation also needs one acceptance record when different developers use different
agents, models, providers, IDEs, and execution environments.

## Decision

RoleFlock is the independent delivery-assurance authority for AI-generated software
changes.

Coding agents are treated as untrusted proposers and bounded workers. They may investigate,
plan, implement, review, or explain work according to their role, but their output is a
claim until RoleFlock validates it against deterministic policy and independently captured
evidence.

RoleFlock owns these authoritative boundaries:

1. **Intent authority** — the versioned Change Contract records the authorised outcome,
   acceptance criteria, prohibited outcomes, scope, risk, and required evidence.
2. **Decision authority** — the versioned Execution Plan records implementation decisions.
   The planner owns plan changes; the executor cannot silently revise them.
3. **Action authority** — RoleFlock grants scoped filesystem, command, network, credential,
   and external-side-effect permissions outside model prompts.
4. **Verification authority** — required verification runs independently from the writer
   against a frozen specification and a commit-bound clean workspace.
5. **Policy authority** — deterministic policy evaluates whether evidence, independence,
   approvals, and risk requirements are satisfied.
6. **Acceptance authority** — only an authorised human or organisation policy may accept,
   merge, release, waive, or revoke a change.
7. **Provenance authority** — the Change Passport binds authorised intent, approved plan,
   result commit, verification, policy, disclosures, and approvals into a portable
   attestation.

The primary product promise is:

> Use any coding agent. RoleFlock turns its work into a contract-bound, independently
> verified, policy-approved change that is safe to review and ship.

The short positioning is:

> Your agents write. RoleFlock decides what is allowed to ship.

## Authority model

```text
Human or organisation authority
        │
        ▼
Authorised Change Contract
        │
        ▼
Planner-owned Execution Plan
        │
        ▼
Bounded coding agent / executor
        │
        ▼
Independent verification evidence
        │
        ▼
Deterministic policy decision
        │
        ▼
Human or organisation acceptance
        │
        ▼
Signed Change Passport
```

No model output may move directly to acceptance without passing the required boundaries.

## Trust boundaries

### Coding agents

Coding agents are not trusted to:

- authorise requirements;
- expand their own permissions;
- weaken required verification;
- validate their own provenance;
- approve their own result.

Model quality affects productivity, but it does not change this trust classification.

### Deterministic RoleFlock runtime

The runtime is trusted to:

- validate schemas and artifact hashes;
- enforce state transitions and role permissions;
- issue and revoke scoped grants;
- invoke exact deterministic checks;
- capture events and evidence truthfully;
- reject incomplete or invalid assurance.

The runtime must fail closed when a required decision or evidence item is unknown.

### Local installation

A local RoleFlock installation may issue a local self-attestation. This proves integrity
relative to that installation identity but does not create independent organisation trust.
The UI and exported passport must label this assurance level explicitly.

### Organisation authority

A future hosted or self-hosted organisation authority plane may establish:

- trusted runner identities;
- central policy;
- RBAC and approval authority;
- key rotation and revocation;
- durable transparency and audit history.

Organisation-trusted assurance must not be inferred from a local self-attestation.

## Product boundary

RoleFlock will build and own:

- Change Contracts and Execution Plans;
- role authority and feedback routing;
- permission and credential envelopes;
- independent verification;
- policy evaluation;
- approval identities;
- Change Passports;
- cross-agent outcome history;
- review and merge decisions.

RoleFlock will integrate with, rather than attempt to replace:

- coding models;
- IDEs and interactive agent conversations;
- Git hosting and branch protection;
- CI systems;
- policy engines;
- signing and software-provenance standards;
- SIEM and observability backends.

## Product invariants

The following are mandatory:

1. Every new write task has an authorised Change Contract.
2. Every executor attempt is pinned to one approved Execution Plan version.
3. The executor cannot revise the plan or consume raw stakeholder feedback.
4. Planner, critic, and verifier roles are read-only.
5. Feedback that changes intent or implementation decisions returns to the planner or
   contract authority.
6. Required verification cannot be satisfied by the executor's own claim.
7. Acceptance binds the exact contract, plan, and result commit.
8. A provider fallback cannot weaken permissions, privacy, verification, or required
   independence.
9. Unknown or missing assurance is displayed as unknown or missing, never inferred as PASS.
10. Local self-attestation and organisation-trusted attestation remain visibly distinct.

## Consequences

### Positive

- RoleFlock remains useful as coding models and IDEs improve.
- Users can keep their preferred coding agents and interaction loops.
- The product aligns with reviewers, clients, platform teams, and organisations that must
  trust changes created by another party.
- Provider neutrality becomes a structural property rather than a model-picker feature.
- Verification and approval can be evaluated consistently across tools.
- Historical verified outcomes can support independent role and model recommendations.

### Negative

- RoleFlock adds deliberate friction before acceptance.
- Independent verification requires additional compute, storage, and workspace lifecycle.
- Strong organisation assurance eventually requires shared identity and signing
  infrastructure beyond a single local process.
- Existing graph and evidence concepts require migration.
- Some low-risk users will prefer to bypass RoleFlock and work directly in their agent.

### Neutral

- Parallel execution, worktrees, provider routing, and recovery remain required, but they
  are supporting capabilities rather than the primary differentiator.
- Multi-agent workflows remain available only when they improve evidence, independence, or
  throughput for a specific task.

## Alternatives considered

### Compete as a better multi-agent orchestrator

Rejected as the primary position. Parallel agents, roles, worktrees, and background tasks
are rapidly becoming native provider capabilities. They remain implementation parity.

### Compete as an interactive coding environment

Rejected. Direct agent conversations preserve conversational context and provide lower
latency for small feedback.

### Provide audit logs only

Rejected. Vendor products already expose session and audit logs. Logs describe activity
but do not by themselves bind authorised intent, independent verification, and acceptance
to a specific commit.

### Build one proprietary coding agent

Rejected. It would place RoleFlock in direct model competition and remove the neutrality
required for independent assurance.

### Use prompts as the role and policy boundary

Rejected. Prompts can guide behaviour but cannot grant reliable enforcement or independent
authority.

## Acceptance evidence

This ADR is implemented only when:

- new tasks cannot reach a writer without authorised intent and an approved plan;
- required verification is captured independently from the writer;
- a commit-bound Change Passport can be verified outside the web UI;
- external coding agents can participate without gaining acceptance authority;
- product copy presents delivery assurance, not agent count, as the core value.
