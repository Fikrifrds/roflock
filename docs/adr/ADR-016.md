# ADR-016: Role authority and planner-owned feedback routing

**Status:** accepted

**Date:** 28 July 2026

**Depends on:** ADR-014, ADR-015

## Context

Role names alone do not create separation of responsibility. A prompt that calls a model
"executor" cannot prevent it from:

- interpreting an ambiguous requirement;
- choosing a new architecture;
- expanding scope;
- responding directly to stakeholder feedback;
- weakening verification to make its result pass.

The current workflow also permits verifier findings to route directly to the writer. That
turns the verifier into an implicit planner: its prose may contain implementation
instructions that were never reviewed or approved.

RoleFlock needs a protocol in which each role has enforceable inputs, outputs, permissions,
decision ownership, and escalation targets. The protocol must work across models and
providers and must survive fresh invocations where conversation history is absent.

## Decision

RoleFlock defines role authority through structured artifact handoffs and deterministic
runtime enforcement.

The core roles are:

```text
Contract Planner
Contract Authority
Planner
Plan Critic
Plan Approver
Executor
Deterministic Test Runner
Verifier
Release Approver
```

Optional specialists may be inserted when policy requires them, but they cannot bypass the
core decision owners.

## General role contract

```typescript
interface RoleAuthorityContract {
  role: RoleId;
  purpose: string;
  requiredInputs: ArtifactRequirement[];
  requiredOutputs: ArtifactRequirement[];
  allowedActions: StructuredActionClass[];
  forbiddenActions: StructuredActionClass[];
  ownedDecisions: DecisionClass[];
  escalationTargets: RoleId[];
  completionCriteria: ArtifactPredicate[];
  permissionProfile: PermissionProfileRef;
}
```

The runtime rejects a role start when required inputs are absent, stale, invalid, or not
authorised. It rejects completion when required outputs fail schema or semantic validation.

Prompts restate the role contract, but the enforceable boundary is:

- artifact validation;
- graph state;
- filesystem and network policy;
- command policy;
- credential scope;
- approval fingerprints.

## Role ownership

### Contract Planner

Owns:

- converting briefs and authority sources into a draft Change Contract;
- identifying conflicts and clarification questions.

Does not own:

- contract authorisation;
- implementation decisions;
- source changes.

Output:

- draft Change Contract;
- conflict and clarification records.

### Contract Authority

Owns:

- authorising, rejecting, revising, withdrawing, or waiving contract requirements.

The authority is an authorised human or organisation policy, never the drafting model.

Output:

- authorised contract hash or typed rejection.

### Planner

Owns:

- repository investigation;
- implementation decisions;
- Execution Plan creation and revision;
- verification design unless delegated to a test designer;
- resolution of executor questions;
- classification and resolution of verifier findings;
- escalation when a finding changes authorised intent.

Permissions:

- repository and document reads;
- policy-approved read-only inspection commands;
- no source writes.

Output:

- proposed or revised Execution Plan;
- decision log;
- verification specification;
- escalation or clarification request when necessary.

### Plan Critic

Owns:

- independent challenge of plan completeness, safety, scope, and verification quality.

Does not own:

- plan mutation;
- approval authority;
- executor direction.

Output:

- criterion- and plan-step-scoped findings;
- recommend approve or revise.

Every finding returns to the planner.

### Plan Approver

Owns:

- approval or rejection of the exact plan hash;
- policy exception approval when explicitly authorised.

The approver may be a human or deterministic policy for eligible low-risk plans.

### Executor

Owns:

- performing approved plan steps;
- producing the result commit and Execution Report;
- detecting and reporting ambiguity or deviation.

The executor does not own implementation decisions. It follows the plan.

Permissions:

- write access only to planned allowed paths in its leased worktree;
- commands and network access only when granted by the plan and policy;
- no access to contract or plan mutation APIs;
- no acceptance or verification authority.

The executor must stop and escalate when:

- a required file or operation is absent from the plan;
- repository state contradicts an assumption;
- a new dependency, migration, API, schema, product, security, or architecture decision is
  needed;
- a test can pass only by weakening required verification;
- stakeholder feedback would change implementation;
- the planned result cannot satisfy the contract.

Output:

- result commit;
- structured Execution Report;
- Plan Deviation or Plan Clarification Request when blocked.

### Deterministic Test Runner

Owns:

- exact execution of approved verification commands;
- truthful capture of exit state, logs, environment, and artifact digests.

It is deterministic infrastructure, not an LLM. It cannot:

- edit files;
- select alternative tests;
- interpret requirements;
- issue a release verdict.

### Verifier

Owns:

- criterion-by-criterion assessment of result evidence;
- independent findings;
- recommendation of pass, fail, or conditional.

Permissions:

- read-only clean verifier workspace;
- approved verification tools through the deterministic runner;
- no source writes or repair credentials.

The verifier does not own:

- plan revision;
- implementation;
- direct executor instruction;
- final acceptance.

Output:

- structured criterion verdicts;
- evidence references;
- findings routed to the planner;
- PASS recommendation only when required evidence is present.

### Release Approver

Owns:

- final accept, reject, conditional accept, revision request, merge, or release decision
  according to its authority.

Input:

- review packet;
- Change Passport candidate;
- unresolved risk and policy decisions.

The release approver does not receive model reasoning by default.

## Artifact handoff

```text
Brief and authority sources
→ Contract Planner
→ draft Change Contract
→ Contract Authority
→ authorised Change Contract
→ Planner
→ proposed Execution Plan
→ Plan Critic
→ findings
→ Planner
→ revised plan
→ Plan Approver
→ approved Execution Plan
→ Executor
→ result commit + Execution Report
→ Test Runner and Verifier
→ verification attestations and findings
→ Planner when revision is needed
→ Release Approver when all required criteria pass
```

Conversation text may explain an artifact, but cannot replace a required artifact.

## Feedback routing

All stakeholder feedback is persisted as a structured `FeedbackItem` before it affects a
run.

```typescript
interface FeedbackItem {
  id: string;
  taskId: string;
  source: ActorRef;
  text: string;
  classification?: FeedbackClass;
  targetContractHash?: string;
  targetPlanHash?: string;
  targetCommit?: string;
  status: "received" | "classified" | "routed" | "resolved" | "rejected";
}
```

Feedback classes:

```text
requirement_change
implementation_preference
implementation_defect
plan_gap
verification_gap
policy_exception
interactive_cosmetic_change
unknown
```

Routing:

| Class | First decision owner |
|---|---|
| Requirement change | Contract Authority with Planner analysis |
| Implementation preference | Planner |
| Implementation defect | Planner, unless deterministic repair envelope applies |
| Plan gap | Planner |
| Verification gap | Planner or Test Designer |
| Policy exception | Authorised policy owner |
| Interactive cosmetic change | Planner, or explicit IDE handoff followed by plan re-entry |
| Unknown | Planner for classification or human clarification |

Raw feedback is never appended to an executor prompt.

## Verifier and test failure routing

Default:

```text
Verifier finding
→ Planner
→ revised plan, contract clarification, or finding rejection with reason
→ optional approval
→ Executor
```

A deterministic test failure may route directly to the executor only when all of these are
true:

1. the failure class is named in the approved repair envelope;
2. the repair uses existing allowed paths and operation classes;
3. no new product, architecture, dependency, migration, schema, API, security, or privacy
   decision is needed;
4. contract and plan remain sufficient;
5. retry, cost, and time budgets remain;
6. deterministic policy returns `repair_allowed`.

This exception is a typed graph edge. Verifier prose can never activate it.

## Plan revision behaviour

When planner action is required:

1. new writer scheduling stops;
2. a running executor reaches a safe cooperative stop;
3. the planner receives the exact current contract, plan, result, and finding artifacts;
4. the planner issues a new plan version or escalation;
5. required critique/approval runs again;
6. the executor receives only the newly approved plan;
7. verification binds to the new plan hash.

The old plan and evidence remain available for audit.

## Same-model role assignment

Role separation is primarily an authority and invocation boundary, not automatically a
model boundary.

Low-risk tasks may use the same model for planner and executor when:

- invocations are separate;
- planner is read-only;
- executor is pinned to the approved plan;
- verification remains a separate invocation;
- policy permits it.

Higher-risk tasks may require different models, model families, providers, or runners.
Those independence rules are defined by policy and ADR-019.

No role may inherit another role's permissions merely because the same model fills both.

## Graph validation

A valid new graph must reject:

- executor without an approved plan artifact;
- executor receiving a raw FeedbackItem as prompt context;
- planner, critic, or verifier with write permission;
- verifier-to-executor `on_needs_changes` edges;
- direct test-failure repair edges without a repair-envelope predicate;
- acceptance without complete contract, plan, verification, and policy artifacts;
- a role completing without schema-valid outputs;
- a provider fallback that violates the role permission or independence policy.

## Consequences

### Positive

- executor behaviour becomes auditable against a stable plan;
- feedback does not lose authority or context across providers;
- planner and executor quality can be measured separately;
- verification findings cannot silently become implementation decisions;
- models can be replaced without changing the role protocol.

### Negative

- planner revisions add latency;
- strict executors may stop more often when plans are incomplete;
- structured artifacts require provider output validation and repair;
- graph migrations are required.

The added stops are intentional signals of plan quality. RoleFlock should reduce them by
improving planning and recommendation, not by giving executors silent discretion.

## Alternatives considered

### Let the executor make reasonable decisions

Rejected because "reasonable" is unbounded, unreviewed planning authority.

### Send verifier findings directly to executor

Rejected because it bypasses planner ownership and allows verifier prose to revise the plan.

### Use one lead model that controls everything

Rejected because it collapses separation of duties and makes assurance dependent on one
model's memory and compliance.

### Require a different provider for every role

Rejected as a universal rule because low-risk work may not justify the cost. Independence
is risk-based, while authority separation is always required.

## Implementation requirements

- `packages/role-protocol`;
- role authority schemas and validators;
- artifact-gated graph nodes;
- feedback persistence and classification;
- planner revision state machine;
- repair-envelope policy;
- role-specific context compiler inputs;
- permission profiles enforced by adapters and runtime;
- compatibility aliases for legacy graph runs.

## Acceptance evidence

This ADR is implemented when:

- executor cannot start without an approved plan hash;
- executor cannot consume raw feedback;
- verifier findings schedule planner work;
- planner, critic, and verifier writes fail outside model control;
- repair routing succeeds only through the deterministic predicate;
- a plan revision safely stops stale execution and pins the replacement attempt;
- graph validation rejects every invalid shortcut listed above.
