# ADR-019: Deterministic role recommendation and outcome scoring

**Status:** accepted

**Date:** 28 July 2026

**Depends on:** ADR-014, ADR-016, ADR-017

## Context

Developers often do not know which installed provider/model should serve as planner,
executor, critic, or verifier. Model capability changes quickly, provider catalogues use
different names and effort controls, and subscription quota may change availability during
a task.

Static defaults are useful for onboarding but become stale. Asking an LLM to choose the
roster is also insufficient because:

- the choice is not reproducible;
- rationale may be invented after the choice;
- hard privacy, permission, and independence requirements may be missed;
- provider marketing claims may be treated as measured quality;
- the selection cannot be audited or compared over time.

RoleFlock needs recommendations that are safe on first use and improve from verified local
outcomes without silently changing a running task.

## Decision

RoleFlock recommends role rosters through a deterministic, versioned pipeline:

```text
Task and policy requirements
→ provider/model capability discovery
→ hard-constraint filtering
→ independence constraint solving
→ deterministic role scoring
→ fallback validation
→ explained recommendation
→ user or policy approval
→ roster pinned to task
```

An LLM may help explain a completed recommendation in plain language, but it cannot select
or reorder candidates outside the deterministic result.

## Recommended objects

The engine recommends:

- required and optional roles;
- provider/model for each role;
- effort level;
- fallback order;
- required independence relationships;
- expected cost and latency class;
- confidence and evidence sources;
- known capability gaps.

The smallest sufficient role roster is preferred.

## Model Capability Profile

```typescript
interface ModelCapabilityProfile {
  providerId: string;

  capabilities: {

  };

  traits: Partial<Record<ModelTrait, ScoredTrait>>;
  constraints: ProfileConstraint[];
  evidenceSources: CapabilityEvidenceSource[];
}

type ModelTrait =
  | 'planning_depth'
  | 'instruction_adherence'
  | 'repository_navigation'
  | 'patch_precision'
  | 'tool_reliability'
  | 'implementation_strength'
  | 'test_reasoning'
  | 'critical_review'
  | 'security_reasoning'
  | 'long_context'
  | 'speed'
  | 'cost_efficiency';

interface ScoredTrait {
  score: number; // 0..1
  confidence: number; // 0..1
  source: 'provider_reported' | 'curated' | 'observed' | 'user_asserted';
  sampleSize?: number;
}
```

Unknown values remain absent. They are never converted to a fabricated neutral score.

## Evidence source precedence

Sources have different authority:

1. hard runtime capability detection for executable requirements;
2. organisation-observed verified outcomes when sample and confidence thresholds pass;
3. versioned curated RoleFlock profile;
4. user/organisation assertion;
5. provider-reported descriptive metadata.

Precedence is trait- and capability-specific. A provider capability probe may establish
that a CLI can write, while observed outcomes establish how reliably one model follows
plans.

Provider marketing statements are never labelled verified performance.

## Role requirement profiles

```typescript
interface RoleRequirementProfile {
  role: RoleId;
  requiredCapabilities: CapabilityPredicate[];
  minimumTraits: Partial<Record<ModelTrait, number>>;
  weights: Partial<Record<ModelTrait, number>>;
  maximumUnknownRequiredTraits: number;
  permissionProfile: PermissionProfileRef;
  independenceRequirements: IndependenceRequirement[];
}
```

### Planner

Prioritises:

- planning depth;
- instruction adherence;
- repository navigation;
- long context;
- structured output.

Must support the read-only invocation mode and schema-valid plan output.

### Executor

Prioritises:

- instruction adherence;
- implementation strength;
- patch precision;
- tool reliability.

Must support a writer-compatible adapter, worktree permission envelope, and structured
Execution Report.

Raw coding creativity is not a positive executor trait when it causes plan deviation.

### Plan Critic

Prioritises:

- critical review;
- contradiction detection;
- test reasoning;
- independence from planner where policy requires.

### Verifier

Prioritises:

- evidence discipline;
- test reasoning;
- critical review;
- instruction adherence;
- independence from executor.

Verifier capability is measured by useful accepted findings and escaped issues, not the
length or severity of its prose.

## Hard constraints

A candidate is ineligible when any required condition fails:

- provider unavailable, unhealthy, or unauthenticated;
- active cooldown;
- missing writer/patch/tool/headless/structured-output capability;
- privacy or data-residency policy forbids provider;
- role permission profile cannot be enforced;
- context capacity is known to be insufficient;
- required effort is unsupported;
- task budget policy forbids expected cost class;
- independence policy would be violated;
- model/provider is disabled by the user or organisation.

Unknown required capability fails closed unless policy explicitly permits an exploratory
run.

Hard constraints apply equally to primary candidates and fallbacks.

## Independence

```typescript
type IndependenceProperty =
  | 'separate_invocation'
  | 'different_model'
  | 'different_model_family'
  | 'different_provider'
  | 'different_runner';
```

Default minimums:

| Risk     | Planner vs executor       | Planner vs critic            | Executor vs verifier          |
| -------- | ------------------------- | ---------------------------- | ----------------------------- |
| Low      | Separate invocation       | Critic optional              | Separate invocation           |
| Medium   | Separate invocation       | Different model preferred    | Different model preferred     |
| High     | Different model preferred | Different model family       | Different model family        |
| Critical | Different model family    | Different provider preferred | Different provider and runner |

Organisation policy may strengthen these defaults. It may weaken only preferred, not
required, separation unless an explicit policy exception is approved.

Independence considers actual model family, provider, and runner after fallback. A fallback
that collapses required separation is ineligible.

## Deterministic scoring

Eligible candidates are scored with a versioned formula:

```text
base fit
= sum(role trait weight × effective trait score)

effective trait score
= score × confidence

adjustments
+ verified success for matching task class
+ availability/quota confidence
+ explicit organisation preference
- expected cost penalty
- expected latency penalty
- unknown optional-trait penalty
- correlation penalty where separation is preferred
- recent failure penalty
```

Formula weights and normalisation are stored with `scoringVersion`.

Tie-breaking order:

1. higher constraint confidence;
2. higher observed verified success confidence;
3. lower expected cost under equal quality band;
4. lower expected latency;
5. stable provider/model ID ordering.

Identical inputs and versioned profiles must produce identical ranking.

## Task classification

Recommendations use task features available before execution:

- task type and risk;
- languages and repository size;
- expected paths/components;
- security, auth, database, migration, dependency, UI, or browser signals;
- test maturity;
- requirement ambiguity;
- expected context;
- privacy and client policy;
- cost/time budget.

Task classification is stored and versioned. A model may extract candidate signals, but
deterministic code validates and records the final features used by scoring.

## Cold start

Before organisation outcomes exist:

- use versioned curated profiles;
- show source date and confidence;
- prefer instruction adherence and tool compatibility over benchmark prestige;
- use deeper reasoning for planning where budget permits;
- preserve required verifier independence;
- provide at least one eligible fallback when possible;
- label recommendations low or medium confidence rather than claiming universal best.

Curated profiles update independently from task state. Existing task rosters remain pinned.

```typescript
  rollback?: ObservationMetric;
  interventionCount?: number;
  latencyMs?: number;
  actualCostUsd?: number;
  shadowCostUsd?: number;

```

Metrics remain attributable to their role:

- plan gaps reduce planner outcome;
- plan deviations reduce executor outcome;
- false-positive or missed findings affect verifier outcome;
- infrastructure failures do not automatically count as model quality failure.

## Statistical safeguards

Observed outcomes influence ranking only when:

- minimum sample size for matching task class is reached;
- confidence interval or configured confidence threshold is satisfied;
- runs are not simulation/fake;
- outcomes are not unresolved;
- observation and scoring versions are compatible;
- organisation has not excluded the data.

RoleFlock reports association, not causation. It does not claim one model caused an outcome
when task, prompt, provider, environment, or policy also changed.

Recent evidence may be weighted more strongly through an explicit versioned decay function.

## Pinning and fallback

The accepted roster is pinned to the task:

```typescript
interface PinnedRoleRoster {
  recommendationId: string;
  scoringVersion: string;
  profileVersions: Record<string, string>;
  assignments: RoleAssignment[];
  acceptedBy: ActorRef;
  acceptedAt: string;
}
```

Running tasks never change assignments because a profile or score updates.

Fallback occurs only for an eligible prevalidated candidate and records:

- failed candidate and reason;
- selected fallback;
- maintained capabilities and independence;
- cost/quality policy impact.

If no eligible fallback exists, the task pauses instead of silently weakening assurance.

## User experience

For every role the UI shows:

- recommendation;
- provider/model/effort;
- capability fit;
- independence relationship;
- confidence;
- evidence source and sample;
- expected cost/latency class;
- fallback order;
- known gaps.

Users may:

- apply recommended roster;
- override one or more roles;
- save an organisation profile;
- provide an override reason;
- restore current recommendations.

Overrides are auditable and still subject to hard constraints unless accompanied by an
authorised policy exception.

## Consequences

### Positive

- developers receive useful model-to-role guidance;
- recommendations remain reproducible and inspectable;
- safety constraints cannot be bypassed by persuasive model prose;
- routing improves from organisation-specific verified outcomes;
- provider neutrality becomes measurable.

### Negative

- curated profiles require maintenance;
- early recommendations have limited confidence;
- observed data can be sparse and confounded;
- strict independence may reduce available fallbacks.

## Alternatives considered

### Hard-code one default model per role

Rejected as the complete solution because catalogues, capabilities, quota, and performance
change.

### Ask the planner model to choose the roster

Rejected because selection would be non-deterministic, unaudited, and potentially
self-serving.

### Route only by cost or quota

Rejected because availability without role fitness can reduce verified success.

### Automatically switch to the latest model

Rejected because latest is not evidence of fitness and would change behaviour without
task-level approval.

### Learn immediately from every run

Rejected because sparse or misclassified outcomes would create unstable routing.

## Implementation requirements

- `packages/role-recommender`;
- capability and trait profile schemas;
- curated profile bundle/versioning;
- provider capability normalisation;
- hard-constraint and independence solvers;
- versioned deterministic scorer;
- recommendation persistence and audit;
- UI rationale and override flow;
- outcome observation pipeline in a later milestone;
- fixtures proving determinism and fallback safety.

## Acceptance evidence

This ADR is implemented when:

- writer-incompatible models cannot be recommended as executor;
- critical independence requirements survive fallback;
- identical inputs produce identical rankings;
- unknown required capability cannot become an implicit PASS;
- every recommendation cites versions, evidence, and confidence;
- user override is durable and audited;
- a running task roster cannot drift after profile updates;
- observed outcomes affect recommendations only after configured safeguards pass.
